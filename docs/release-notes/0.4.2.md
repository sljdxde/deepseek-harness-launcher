## 0.4.2 更新说明

### 修复

- **修复「更新/首装后内置窗口停在 Harness 页面打不开，再也进不去」**：其他机器上更新或首次安装后，内置窗口只显示一张 `Harness 页面打不开 / Could not connect to the server.` 的失败卡片，点菜单「打开」或重载都没用。原因是启动器接管（复用）一个已存在的 dsh 时拿不到它的进程句柄，那个实例后来退出（终端被关掉、旧版本更新留下的孤儿进程被系统回收），启动器却仍然认为自己在运行、端口仍指向那个已经没人监听的地址；而「打开」看到端口没变就只前置窗口、连重载都不做，于是永久卡死。
  - 现在启动器在就绪后持续复核「当前端口上还有 dsh 在应答」：连续 3 次无应答即判定实例已死，自动清掉失效状态与旧认证入口，重新拉起一个受自己管理的实例，内置窗口自动加载新页面，用户不需要点任何东西。
  - 进程还活着但端口卡死（事件循环被占死）同样会被发现，用更长的判定预算处理，避免打断正在跑的回合。
  - 内置窗口一旦报「连不上」，会立刻确认一次服务是否还在，不用等下一轮复核。
  - 认证失败（401）、导航被取消、内容类型错误不会触发重启——那类问题重启解决不了，仍由失败页里的提示引导。

### 平台同步

- **Windows 启动器同步修复**：原先只有「接管实例」有存活看护，且判定失效后没有清空端口，`刷新页面`/`打开` 仍会把窗口指向死地址；自己拉起的实例卡死则完全没有看护。现在两条路径统一纳入看护，阈值与 macOS 对齐。

### 回归

- 新增运行期存活判据的单测（macOS `scripts/test-runtime-health.swift`、Windows `internal/app/runtimewatch_test.go`），并在 `scripts/test.sh` 增加源码守卫，防止这条看护被后续改动误删。
